# Silo API v2 Adoption Implementation Plan

> **For agentic workers:** Use superpowers:executing-plans to implement this plan, or superpowers:subagent-driven-development when delegation is authorized. Steps use checkbox syntax for tracking. This document authorizes no production Silo upgrade or playback command; this session produces the plan only.

**Goal:** Keep Barracks working as Silo retires its legacy business API, then use the v2 contract to improve fleet monitoring, historical accuracy, and operational visibility.

**Architecture:** Preserve the React dashboard, Express service, PostgreSQL storage, and existing provider interface. Introduce per-connection API negotiation and separate wire adapters behind `SiloAPI`; build new fleet history and analytics around explicit server identity. Keep upstream credentials on the backend and publish only permission-filtered Barracks responses.

**Tech Stack:** Node.js, Express, React/Vite, PostgreSQL/Knex, native HTTP fetch, node:test, existing Playwright verification scripts.

**Status:** User approved implementation. Chunk 1 is implemented, locally verified and reviewed on `feat/silo-api-v2`; see [implementation status](../../silo-v2-status.md). Deployment/canary gates remain open. Chunks 2–3 remain planned. Initial migration is read-only against Silo. Later playback controls and session-based events are separate delivery gates.

### What Barracks can gain

| Priority | Barracks feature | Verified upstream surface | Qualification |
| --- | --- | --- | --- |
| P0 | Survive the v1 business API retirement | `/api/v2/system/info`, typed collections, Problem Details, domain capabilities | Contract migration, not a prefix replacement. Health remains a separate retained probe. |
| P1 | More informative live stream cards | `/api/v2/admin/sessions`, `/admin/sessions/capabilities` | Hardware acceleration, tone mapping, source/target audio, client build/channel, execution and egress nodes; some fields already exist in newer v1 and are currently discarded by Barracks. |
| P1 | Recover finalized plays missed while Barracks was offline | `/api/v2/admin/playback-history` | Server-reported attempts include profile, unique session ID, watched seconds, completion, and timestamps. Recovery is limited by upstream retention and attribution. |
| P2 | Fleet trends and per-server playback reliability | `/api/v2/admin/stats`, `/admin/stats/timeseries`, `/admin/stats/playback-activity`, `/admin/stats/top-activity` | These are carried-forward Silo capabilities newly used by Barracks. Sampled/provider aggregates have different semantics from current live sessions and local history. |
| P2 | See resource pressure and worker routing | `/api/v2/admin/system/resources`, `/admin/system/hw-accel`, `/admin/nodes`, `/admin/node-sessions`, `/admin/tasks`, `/admin/jobs` | Node observations are best effort, not additional playback sessions. Optional dependencies can be unavailable. |
| P3 | Pause, resume, message, stop, terminate from Barracks | `/api/v2/admin/sessions/command-capabilities` and session action endpoints | Dedicated permission, operator confirmation, sequenced commands and honest receipt status required. Terminate differs from stop. |
| Gated | Event-driven refresh instead of constant polling | `/api/v2/events/capabilities`, `/events/ws-ticket`, `/events/ws` | Not usable with Barracks' current API-key-only connection model. Requires upstream service-credential support or a separately designed login-session integration. |

**Recommended delivery order:** compatibility → live diagnostics → fleet history → analytics/resources → optional controls. Do not make events a prerequisite. Do not promise a monitoring-only API-key scope that upstream does not yet implement.

### Current Barracks constraints verified in source

- `apps/api/classes/silo/http.js` forces every base onto `/api/v1` and supports GET only. Supplying a `/api/v2` URL currently produces an incorrect nested path.
- `apps/api/classes/silo-api.js` expects bare session/user/library arrays, offset catalog paging, and `seasons`/`episodes` envelopes. V2 uses typed `items` collections and cursor semantics; audit each endpoint separately.
- `apps/api/classes/silo/mappers.js` rejects a session without `content_id`, although v2 permits its absence. One valid unattributed stream must not make an entire server unavailable. Existing numeric conversion also turns explicit null into zero in some paths; preserve unknown values deliberately.
- `apps/api/classes/fleet-service.js` and `fleet-identity.js` use health's `server_id` to exclude physical duplicates. V2 `system/info` contains API/build/digest information, **not** server identity; do not replace identity with a build version or contract hash.
- Live fleet polling is every five seconds. Existing generations fence responses from removed/changed/unavailable connections; preserve this across negotiation and optional requests.
- `docs/multiple-servers.md` explicitly limits persisted history, users, catalog, and statistics to the primary server. `silo-activity-store.js` queries all Silo watchdog rows under one advisory lock; invoking it independently for multiple servers would incorrectly finalize another server's sessions.
